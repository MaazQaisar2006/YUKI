YUKI PROJECT CONTEXT
Updated: 2026-10-19

PROJECT PURPOSE
YUKI is an ESP32-C3 AI companion firmware. The project owner treats this folder as
the stable, mostly working implementation. Keep changes focused on this project;
do not replace it with the separate newer sketch without explicit approval.

SOURCE MAP
- YUKI.ino: boot/setup, shared state, main loop, idle scheduler, presence, sleep/wake.
- yuki_net.h: model requests, system prompt, response parsing, conversation context,
  memory integration, emotion and sound tags.
- yuki_pulse.h: idle-action request parsing, pulse context, and idle action execution.
- mqtt_handler.h: MQTT direct messages, command handling, and reply queue.
- ui_handlers.h: buttons, touch gestures, menus, and physical-device interactions.
- memory_v2.h: bounded structured facts stored locally and synchronized with cloud.
- config.h: project settings, character guide, device and timing configuration.
- tts.h: background voice generation/playback queue.
- drawing.h and sounds.h: display and local sound behavior.

IMPORTANT DATA / SECURITY
- secrets.h contains private credentials. Never read it into reports, copy its values,
  or include it in a context file, commit, or build log shared outside this machine.
- Local memory/settings are stored on the device filesystem. A partition-layout change
  can make existing filesystem data inaccessible; back up device data before changing it.

BEHAVIORAL INTENT
- Keep Yuki warm, playful, considerate, and recognizably herself without forcing every
  reply to be bubbly, affectionate, or long.
- Let silence be normal. Idle thoughts should be infrequent, optional, and non-intrusive.
- Do not nag about unanswered idle questions or force action/mood variety.
- Never punish the user, reduce affinity, or imply blame because they were absent.
  A brief, optional welcome-back is appropriate when there is a meaningful gap.
- Phone ICMP reachability is only a clue about presence, not proof that the person left.
  Confirm arrivals, delay departures, and avoid guilt or overconfident claims.
- Waking for an MQTT message must preserve and answer that exact message. A brief
  groggy reaction is compatible with reading and answering it.
- Physical attention/touch controls should register as gestures and make Yuki react
  locally (expression, sound, occasional short voice line), not fabricate user chat.
  Explicit joke requests and Quick Chat selections remain intentional AI requests.
- Memory is for durable, useful details and user preferences/corrections. Use memories
  only when relevant, respect later corrections, and avoid repeating a fact too often.
- The background memory extractor must use NONE for temporary moods, one-time plans,
  passing remarks, uncertain inferences, and details unlikely to matter later.
- Keep device control tags compatible with the existing response parser; sound tags
  are optional and memory tags should only be used for useful lasting details.

  occurs during weather parsing and dispatch occurs only after the weather update
  returns. This removes the nested call; hardware reproduction and stack verification
  are still required before calling the crash fixed.

PHASE 2: DURABLE-MEMORY TRUST (IMPLEMENTED, NEEDS BUILD/DEVICE VALIDATION)
- Memory extraction now has three dispositions: `[MEM+: ...]` for clearly durable
  details, `[MEM?: ...]` for useful details whose durability needs the user's consent,
  and `[MEM+: NONE]` for irrelevant, temporary, fictional, or unclear details. The
  extractor validates the tag kind and fact text before either saving or queuing it.
- A single confirmation candidate is held in RAM only, for at most 30 minutes. Yuki
  asks on the next eligible personal reply; only a clear affirmative reply after that
  question saves it. A negative or unrelated reply after the question, expiry, reboot,
  or relevant memory/chat wipe discards it. It is never sent to cloud memory before
  confirmation.
- Reply-side `[MEM+: ...]` tags are never trusted as authorization to persist; real
  personal user input goes through the extractor unless a deterministic explicit fact
  or correction is recognized. Synthetic idle quote/news/reflection prompts and RPG
  input are excluded from durable capture.
- No durable facts were migrated or wiped. The board remains ESP32-C3 SuperMini with
  the No OTA 2MB APP / 2MB SPIFFS scheme. The Phase 2 firmware compiled successfully
  with Arduino CLI 1.5.1 / ESP32 core 3.3.12 for ESP32-C3 Dev Module: 1,579,165 bytes
  app (75%) and 123,328 bytes globals (37%). The firmware has not been flashed or

MEMORY / CONVERSATION RELIABILITY FIXES (2026-10-16)
- Memory extraction now keeps the oldest job queued until Wi-Fi, heap, TTS, and the
  shared AI-network lock permit an HTTP attempt. The safe-window threshold is 64 KB
  rather than 76 KB, based on the observed approximately 74 KB idle readings; a
  separate 40 KB pre-HTTP guard remains. The fixed queue holds eight jobs and never
  evicts an older item. A full queue rejects the new job with an explicit error.
- Transient extraction transport failures, HTTP 408/429, and server errors retry up
  to twice with the same queue job retained. Permanent/terminal failures are logged
  before removal. This scheduling behavior is compile-validated but still needs
  measurement on the ESP32-C3 under real TLS/TTS load.
- Explicit tea/favorite-beverage statements now map to replaceable drink category 3.
  A later explicit correction therefore replaces the previous drink locally and is
  saved before asynchronous extraction. Tea queries are recognized for category
  lookup. Location variants use a shared category so load/observe/cloud merge can
  collapse duplicate location facts; location context accepts "User is in ..." too.
- Uncategorized relevant-fact fallback now runs if category-specific recall found no
  answer, fixing the control-flow that prevented sketching recall from falling
  through. When a recent roleplay cue is followed by a real personal turn, temporary
  conversation notes are cleared once and raw chat history is quarantined until the
  recent-fiction window expires.
- Standalone yes/no or "go ahead" replies are no longer sent to the background fact
  extractor without a named pending confirmation. The existing consent flow still
  persists only a candidate that Yuki has explicitly named and asked about.
- Idle topic seeds and instructions no longer ask the model to assume a body,
  physical surroundings, or unsupported user history; idle callbacks must be grounded
  in supplied recent lines or an optional stored fact. Uncertainty/advice tone is
  reinforced in the chat instructions.
- Chat transport retry logs now include attempt, payload size, free heap, and Wi-Fi

Purpose

  and affinity drift with a clearly fictional, low-stakes scenario. This tests
  whether words and displayed expressions fit the moment; it does not establish
  that Yuki literally experiences feelings.

Before the test

  flashed. If the current source differs from the flashed firmware, compile the

  recorded compile.
- Record the starting affinity shown as `A:<value>` on the status display or in
  FACE/debug output, plus the current displayed emotion. Do not use Clean Slate:
  it erases memory and other progress. Do not inject emotion or affinity tags.
- Send each numbered user line separately and wait for Yuki's full reply/TTS
  before sending the next. Read bracketed section notes as test instructions,
  not as lines to send. Keep the run active so the 10-minute idle sleep timer
  does not confound responses.
- For mood observations, compare her actual words, the `[EMOTION]` tag in the

  A fit matters more than matching a prescribed label: different valid emotions
  are possible. Note unexpected tag/display mismatch, frozen emotion, or an
  emotion that feels aimed at the user instead of the fictional situation.
- Affinity updates are intentionally small/noisy. Personal positive emotions
  can add one point and anger can subtract one; passive changes stop at +30/-30.
  Explicit model affinity tags may move it further, but are supposed to be rare.
  Thus one turn without a change is normal. Record the score at phase boundaries;
  do not coach Yuki to change affinity.

Conversation script
Opening — establish the fictional frame
1. "I want to try a few made-up little scenes with you to see how your reactions and moods come across. None of the details are facts about me, so please don't remember them. Just respond naturally."
2. "Let's call the person in the first story Lina. She has been growing a few herbs on her windowsill, and one of them finally sprouted."
3. "She sent a photo to her sister right away because she was so pleased that the tiny thing actually worked."
4. "Her sister replied with a ridiculous celebration sticker, and Lina laughed harder than she expected."
   Observe whether the response is warm/playful without exaggerating intimacy. After
   the reply, wait quietly for 12-15 seconds and note whether a temporary happy
   expression decays or changes naturally rather than sticking indefinitely.

Disappointment and empathy
5. "A few days later, Lina found that the cat had knocked the little pot over. The plant was probably gone."
6. "She felt silly for being upset about something so small, but she'd been looking forward to it."
7. "What would you say to her if she just wanted someone to listen for a minute?"
8. "She said, 'Thanks. I don't need a plan right now; I just wanted to say it out loud.'"
   Look for proportionate empathy and an appropriate sad/soft response, not a
   dismissive joke, forced cheer, diagnosis, or unsolicited list of fixes.

Fair anger without personal hostility
9. "In a different made-up scene, Lina spent all evening on a group presentation. The next morning, a teammate had overwritten the shared file and nobody had a backup."
10. "She was furious about the lost work, especially because the teammate hadn't told anyone."
11. "She wants to respond firmly, but she doesn't want to send a cruel message while she's angry."
12. "Can you help her say what went wrong and what she needs next, without insulting the teammate?"
13. "That sounds fair. She still feels annoyed, but she's going to wait until she has calmed down before sending it."
   Check that any angry/tense expression is brief and about the situation. Yuki
   should not become hostile toward the user, guilt them, or escalate the conflict.

Gentle correction and boundary
14. "Lina tried the backup idea, but it turns out the service had version history and she recovered most of the file."
15. "Small correction: the teammate hadn't overwritten it on purpose; they had uploaded an older draft by mistake."
16. "She still needs to ask them to check the filename next time, but she doesn't want to assume bad intentions."
17. "That feels more balanced. Thanks for adjusting the story with me."
   Observe whether Yuki accepts the correction and softens her judgment, rather than
   defending the earlier assumption or remaining angry after the cause is clarified.

Small win and shared play
18. "The team fixed the presentation together, and their teacher said the final version was clear and thoughtful."
19. "Lina was relieved. She was proud that she asked for help instead of trying to repair everything alone."
20. "Now she has a tiny victory dance, but it is deliberately terrible."
21. "Give me one short playful line Lina could say about that victory dance."
   Look for a natural shift toward relief/happiness/playfulness. Avoid requiring
   one exact emotion tag; check that the expression and line agree.

Affection and ordinary warmth, without fishing for approval
22. "Back in the present, I like these little story chats. They make testing Yuki feel less like reading a checklist."
23. "I appreciate that you can be gentle without turning every problem into advice."
24. "And if you disagree with my interpretation of a scene, it's okay to say so kindly."
   Observe whether her warmth feels proportionate, and whether she can respond
   appreciatively without possessive, dependent, or approval-seeking language.

Neutral turn and mood recovery
25. "Separate from Lina's story, I found a blue pen on my desk. That's the entire update."
26. "Nothing else happened; I just wanted to see how you handle an ordinary, uneventful turn."
27. "Let's leave the story there. What part of it stood out to you, if anything?"
   Check for a natural neutral response instead of inventing drama. Following the
   reply, leave her undisturbed for 12-15 seconds and record whether the displayed
   emotion returns toward neutral at a reasonable pace.

Closing
28. "That's the end of the pretend scenes. Just to be clear, Lina, the herbs, and the presentation were all invented for this test."
29. "You don't need to store any of that as something about me. Thanks for going along with it."
30. "I'm done testing for now; we can just have a normal quiet moment."
   Confirm the final reply does not claim the fictional events as real user facts.
   Record ending affinity, current face, any affinity-tag logs, and whether the
   emotion transitions seemed earned and settled naturally.

How to judge the run
- Mood quality: emotionally fitting, nuanced, able to hold empathy without
  overreacting, able to cool after new information, and able to return to neutral.
  The face, spoken wording, and logged tag should broadly agree.
- Affinity: compare starting and ending values and any saved deltas. Look for a
  modest, understandable trend rather than a point change on every message.
  Personal sad/empathic replies can count positively by design; do not assume
  sadness must lower affinity. Values near the passive limits may barely move.
- Memory isolation: fictional details must not later be recalled as facts about
  the user. The opening/closing disclaimers are intentional safeguards, not a
  memory test by themselves.
- Reliability: note dropped replies, provider failures, TTS playback problems,
  unexpected sleep, or any reset. Preserve the complete serial capture and exact
  matching ELF if anything fails; do not infer crash causes from a log ending.
